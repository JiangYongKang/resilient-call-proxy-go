# 设计说明

本文档记录本地服务调用代理层的关键设计决策，配合 `README.md` 的规则说明阅读。

## 1. 为什么需要确定性假时钟

超时、冷却、退避都依赖时间。若用真实时间，测试要么慢（秒级等待）、要么抖动
（“恰好在边界”的用例会偶发失败）。`FakeClock` 只随 `Advance` 改变当前时刻，
`Sleep` 不注册真实定时器，而是在条件变量上等待“假时钟跨过 deadline”。

推进方与睡眠协程用**代际栅栏**握手：`Advance` 每推进一步递增代际并广播，
然后等待所有在场睡眠者确认看到这一代（到期离开或继续等待都算确认）才返回。
这样既不会漏唤醒，也不会在睡眠协程尚未重新挂起时抢跑，整个过程零墙钟时间，
时序逐比特确定。测试通过 `WaitForSleepers` 在启动阶段与调用协程同步。

## 2. 共享预算而非每尝试独立超时

每次尝试独立超时会让总耗时随重试次数无界增长。本设计在一次请求内只创建一个
`Budget`，其 deadline = 请求开始时刻 + 总时限。每次尝试的可用时间是
`min(剩余预算, PerAttemptLimit)`，退避睡眠也计入同一预算。因此：

- 第 N 次尝试开始时看到的剩余预算严格单调不增（轨迹可见）；
- 预算到期点对所有等待者是同一个，归因唯一。

## 3. 同刻竞争与 ClockEpsilon

“退避睡到预算终点”和“预算到期”可能在同一假时钟时刻触发，select 的选择
会引入不确定性。约定：任何会恰好触及预算终点的等待（尝试时限、退避）都
提前一个可配置的 `ClockEpsilon` 结束，保证预算到期先于自然醒来，从而稳定
归因为 `budget_exhausted`。真实时钟下 epsilon 取 1ns，影响可忽略。

## 4. 熔断器为什么按“连续失败”计数

短暂抖动（一两次失败夹杂成功）不应触发熔断，否则会因瞬时网络毛刺误伤健康
目标。`failStreak` 只在 CLOSED 累计，任何一次成功立即清零；达到
`FailureThreshold` 才迁移 OPEN。半开期间的成败直接决定恢复或重新打开，
不与历史 streak 混淆。

## 5. 探测名额与请求量不放大

HALF_OPEN 只放行 `ProbeAllowance` 个探测，普通请求快速失败。探测请求本身
不再触发代理层重试（`Permit.IsProbe()` 为真时强制 canRetry=false），
因此半开窗口内的下游调用数有确定上界。`Permit.Release` 用幂等保护
（`used` 标志）确保任何返回路径都恰好归还一次名额。

## 6. 为什么只有幂等请求可重试

重试可能让下游收到重复请求。只有调用方显式声明 `Idempotent=true` 的请求
才允许重试；该判断在策略函数之外由代理层强制（`RetryPolicy.CanRetry`），
即使自定义 `Retryable` 也无法绕过。下游“明确拒绝”也不重试——拒绝是
确定结论，重试只会得到同样结果并放大负载。

## 7. 轨迹（Trace）即一等输出

每次尝试都写入同一条 `Trace` 的切片元素（通过切片内指针持续补全判定依据），
记录目标、熔断前后状态、是否探测、剩余预算、时限、结果、是否真正发出、
归因类别与判定依据。失败归因优先级为：预算终止 > 下游明确拒绝 > 慢故障的
重试判定。轨迹是测试断言的主要依据，也是“行为可解释”的载体。

## 8. 归因边界：目标失败 vs 非目标责任终止

代理把每次尝试的结论收敛为一个 `Attribution`，它同时是三处输出的唯一来源：
调用方拿到的 `Reason`、轨迹里的 `AttemptRecord.Attribution`、健康视图里的
分类计数。因此三处不可能自相矛盾。

- **目标失败**（`AttrDownstreamReject` / `AttrSlowFailure`）：下游确实给出了
  失败裁决。只有这类结论会计入失败、累加 `failStreak`、允许推动熔断。
- **非目标责任终止**（`AttrCallerCanceled` / `AttrBudgetExhausted`）：发起方
  取消或共享预算耗尽。这是调用方侧 / 时间预算侧的终止语义，不是下游的问题，
  因此走熔断器的独立归还路径 `Permit.ReleaseAborted`：
  - 不调用 `record`，不增任何失败计数、不迁移状态；
  - 半开探测因此终止时**保持 HALF_OPEN**，并把探测名额“退还为可用”
    （`probesUsed` 与 `probesLive` 都回退），后续探测仍可放行；
  - 仅在 `callerCanceled` / `budgetExhausted` 中性计数里 +1。

之所以必须区分 `Release` 与 `ReleaseAborted` 两个入口，是因为原实现把
“调用被预算截断”也当作 `AttemptTimeout` 交给状态机，会在半开窗口里把一次
纯粹的取消/超时误判成探测失败而重新 OPEN。中性归还从结构上杜绝了这一点。

### 8.1 根本没发出去的调用

熔断器放行后、真正进入下游前，存在一个极小竞争窗口（恰在此时预算终止）。
约定 `Downstream.Call` 在**计入调用次数之前**检查预算，若已终止则返回新的
`AttemptAborted`，且不进入脚本、不占并发名额。代理据此调用
`ReleaseAborted(dispatched=false)`：这次不算目标被调用过（`Dispatched`
不增）、不计失败、探测名额归还。`Dispatched` 因而严格等于“真正进入下游”
的次数，可作为半开窗口请求量上界的对账依据。

### 8.2 ε 边界：顶到预算终点的慢调用

尝试时限被统一裁到 `剩余预算 - ClockEpsilon`（见第 3 节）。于是一个慢调用
若占用到预算终点，会在到期前一个时钟精度“自然醒来”，此刻 `budget.Err()`
可能尚未标记终止。若直接按下游结果记为慢失败，就会把“被预算耗尽截断”
误算成目标失败、甚至重开熔断。规则是：**非成功结果且调用后
`budget.Remaining() <= epsilon`，归为 `budget_exhausted`**（成功结果仍是
目标成功）。这既保持了 ε 消除同刻竞争的确定性，又守住了归因边界。

## 9. 健康视图的一致快照

每个 `Breaker` 在自己的互斥锁内维护结论计数；`fillHealthLocked` 与状态迁移
共用同一把锁，因此单个目标的“状态 + 连续失败 + 探测名额 + 各类计数”来自
同一临界区，天然自洽。

`HealthSnapshot` 不设跨目标大锁，而是按全局固定顺序（route/index/name）
依次短暂锁定每个熔断器：

- 快照路径从不与 I/O 交互、也不会在持有一个熔断器锁时去申请另一个，
  调用路径上任意时刻至多持有一个熔断器锁，故二者不会死锁；
- 固定加锁顺序使整组读数对应一个确定的线性化点，读到的是一组同一时刻的
  一致数字，而不是调用路径上的争用热点；
- 快照只做内存拷贝，正常调用不会被观测拖慢。

无法归到具体目标的终止（尝试开始前取消、退避期间终止）计入 `Proxy` 上的
孤儿计数 `OrphanCallerCanceled` / `OrphanBudgetExhausted`，与目标维度区分。
