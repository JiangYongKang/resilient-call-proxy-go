# 设计说明

本文档记录本地服务调用代理层的关键设计决策，配合 `README.md` 的规则说明阅读。

## 1. 为什么需要确定性假时钟

超时、冷却、退避都依赖时间。若用真实时间，测试要么慢（秒级等待）、要么抖动
（“恰好在边界”的用例会偶发失败）。`FakeClock` 只随 `Advance` 改变当前时刻，
`Sleep` 不注册真实定时器，而是在条件变量上等待“假时钟跨过 deadline”。

推进方与睡眠协程用**代际栅栏**握手：`Advance` 每推进一步递增代际并广播，
然后等待所有在场睡眠者确认看到这一代（到期离开或继续等待都算确认）才返回。
这样既不会漏唤醒，也不会在睡眠协程尚未重新挂起时抢跑，整个过程零墙钟时间，
时序逐比特确定。测试通过 `WaitForSleepers` 在启动阶段与调用协程同步。

## 2. 共享预算而非每尝试独立超时

每次尝试独立超时会让总耗时随重试次数无界增长。本设计在一次请求内只创建一个
`Budget`，其 deadline = 请求开始时刻 + 总时限。每次尝试的可用时间是
`min(剩余预算, PerAttemptLimit)`，退避睡眠也计入同一预算。因此：

- 第 N 次尝试开始时看到的剩余预算严格单调不增（轨迹可见）；
- 预算到期点对所有等待者是同一个，归因唯一。

## 3. 同刻竞争与 ClockEpsilon

“退避睡到预算终点”和“预算到期”可能在同一假时钟时刻触发，select 的选择
会引入不确定性。约定：任何会恰好触及预算终点的等待（尝试时限、退避）都
提前一个可配置的 `ClockEpsilon` 结束，保证预算到期先于自然醒来，从而稳定
归因为 `budget_exhausted`。真实时钟下 epsilon 取 1ns，影响可忽略。

## 4. 熔断器为什么按“连续失败”计数

短暂抖动（一两次失败夹杂成功）不应触发熔断，否则会因瞬时网络毛刺误伤健康
目标。`failStreak` 只在 CLOSED 累计，任何一次成功立即清零；达到
`FailureThreshold` 才迁移 OPEN。半开期间的成败直接决定恢复或重新打开，
不与历史 streak 混淆。

## 5. 探测名额与请求量不放大

HALF_OPEN 只放行 `ProbeAllowance` 个探测，普通请求快速失败。探测请求本身
不再触发代理层重试（`Permit.IsProbe()` 为真时强制 canRetry=false），
因此半开窗口内的下游调用数有确定上界。`Permit.Release` 用幂等保护
（`used` 标志）确保任何返回路径都恰好归还一次名额。

## 6. 为什么只有幂等请求可重试

重试可能让下游收到重复请求。只有调用方显式声明 `Idempotent=true` 的请求
才允许重试；该判断在策略函数之外由代理层强制（`RetryPolicy.CanRetry`），
即使自定义 `Retryable` 也无法绕过。下游“明确拒绝”也不重试——拒绝是
确定结论，重试只会得到同样结果并放大负载。

## 7. 轨迹（Trace）即一等输出

每次尝试都写入同一条 `Trace` 的切片元素（通过切片内指针持续补全判定依据），
记录目标、熔断前后状态、是否探测、剩余预算、时限、结果、判定依据。
失败归因优先级为：预算终止 > 下游明确拒绝 > 慢故障的重试判定。
轨迹是测试断言的主要依据，也是“行为可解释”的载体。

## 8. 归因边界：非目标责任终止不计入目标失败

一次尝试被**发起方取消**或**共享预算耗尽**截断时，其结果不含任何关于
目标健康的信息——下游可能根本没响应，甚至调用根本没发出去。把这类终止
记为目标失败会污染熔断信号（半开探测被取消就误重开，等于让调用方自己的
取消放大了故障）。因此 `Permit` 提供两种归还路径：

- `Release(result)`：下游给出了可归因于目标的裁决（成功/拒绝/慢故障/
  自身超时），正常驱动状态机与健康计数；
- `Abandon(reason)`：非目标责任终止。名额（含探测名额）中立归还，
  **不触碰** `failStreak`、**不驱动**任何状态迁移，只在健康视图中记入
  `AbortedByCaller`/`AbortedByBudget`。

被取消的探测为什么不消耗探测额度：探测的价值是换取目标健康信息，被取消的
探测什么信息也没换到；若不退额度，熔断器会卡死在 HALF_OPEN（名额耗尽且
再无任何事件能推动它）。退回额度（`probesUsed` 与 `probesLive` 同时归还）
保证后续请求可以重新探测，同时半开窗口内**在途**探测数仍严格 ≤ 名额，
请求量上界不变。

代理层在“调用下游前”与“调用返回后”各检查一次预算：前者覆盖“刚放行就赶上
预算终止”（不算目标被调用过），后者把被预算截断的下游 TIMEOUT 重新归类为
非目标责任终止。归因判断集中在代理层这一处，返回原因、轨迹 `Decision`、
健康计数由此必然一致。

## 9. 健康视图为什么放在熔断器的锁里

健康快照要求“一组数字是同一时刻的一致快照”，且查询不能与调用路径互相
拖慢。熔断器本来就持有一把锁保护状态机（`state`/`failStreak`/`probes*`），
把归类计数也放进同一临界区后：

- 计数与状态天然同源，`Snapshot()` 在锁内一次读出即一致快照，无需额外
  同步手段（无原子变量拼接、无读写锁层级）；
- 调用热路径不新增任何锁——计数只是 `record`/`Allow`/`abandon` 临界区里
  已有的自增操作；
- 查询（`Proxy.Health`/`HealthAll`）只读，与调用并发安全。

一个已知的取舍：预算终止大多在检查点（新尝试前/退避后）被裁决——
`ClockEpsilon` 纪律保证等待不会越过预算终点——此时没有占用名额的在途
尝试，健康视图只如实反映已发生的目标裁决，不为“请求级终止”虚构一次
目标级计数；只有真正截断了在途尝试的终止才计入 `Aborted*`。
